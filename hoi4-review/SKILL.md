# HOI4 交叉审查（Review，可选门）

## Overview

**管什么**：在大型里程碑或发布前，用"另一双眼睛"审查 mod——7 项检查清单（内容/平衡/AI/性能/规范/发布绑定/查重），产出**分级审查报告**。

**适用门（可选，不强制）**：
- 大型 mod 里程碑
- 发布前最终闸门
- 用户主动要求

**何时不用**：
- 小型增量改动 → **不强制进入**本门，直接走验证即可
- 还在做功能 → **hoi4-executing-plans**
- 发现 bug 要修 → **hoi4-systematic-debugging**

## 入口

来自 **hoi4-verification-before-completion** 的建议（大型 mod）/ 用户主动要求 / 发布前。

## 7 项审查清单

**1. 内容审查**：依赖链完整性 / 本地化 100% / GFX 注册 / 编码——复用 **hoi4-verification-before-completion** 清单，以**挑剔视角重跑**（不只是"有没有报错"，还要"做得对不对"）。

**2. 平衡审查（钢4 特有）**：数值基线对照**原版同类**（攻击力/造价/耗时/研究成本），防超标；大型 mod 制定多轮平衡评估计划。

**3. AI 行为审查**：AI 会不会点新国策 / 造新装备 / 触发新决议——检查 `ai_will_do`、AI 策略文件（AI 战略见 **hoi4-advanced-systems**）。

**4. 性能审查**：脚本每 tick 开销——对照 `references/脚本性能优化教程（wiki译文）.md`（Paradox 前技术总监的真实性能案例：作用域检查、重复求值等）。

**5. 规范审查**：命名规范（`my_mod_` 前缀）、目录位置、GFX 命名——Rt56 教训：**肖像丢失全是没按命名规范**。

**6. 发布绑定审查**：changelog/补丁说明与 git 提交绑定、版本号递增（Rt56 做法）——详见 `references/10-发布与创意工坊.md`。

**7. 查重**：与已有 mod/原版内容重复（KR 做法：issue 先查重）。

## 输出：审查报告

- 发现项**分级**：**阻断**（必须修才能发布）/ **建议**（应该修）/ **可选**（可留）
- 修复项清单：每项 = 发现 + 位置 + 建议修法
- 阻断项未清零不进入发布

## 出口

修复项清单 → **hoi4-executing-plans**（照单执行）；需要改设计 → **hoi4-writing-plans**（修订计划）。

## 人机分工

- **单人**：自我对抗审查（自己当另一双眼睛）+ **关键项请用户人工确认**（平衡手感、主题贴合度 AI 判断不了）
- **团队**：真实交叉审查协议（另一成员检查内容 + 多轮平衡因素评估，仿 Rt56/KR 做法）

## 常见错误表

| 现象 | 原因 | 修复 |
|---|---|---|
| 审查只挑报错 | 没做平衡审查 | 平衡基线对照原版同类数值 |
| AI 行为问题发布后才发现 | AI 行为审查被跳过 | 检查 ai_will_do 与 AI 策略 |
| 大 mod 卡顿 | 性能审查无基线 | 对照性能教程查每 tick 开销 |
| 肖像/图标丢失 | 命名规范没查 | GFX 命名与注册核对（大小写敏感） |
| 修复优先级混乱 | 审查报告无分级 | 阻断/建议/可选分级 |
| 小型 mod 被强制全套审查 | 门过重 | 小型增量不强制进入本门 |
