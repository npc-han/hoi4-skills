# HOI4 设计先行（Brainstorming）

## Overview

**管什么**：把模糊的 HOI4 mod 想法变成**用户批准的明确设计**——需求提问清单、方案提案、规格文档（spec）。钢4 版"设计先行"：任何创作任务，先设计、后批准、再动手。

**何时用**：
- 用户说"做个新国家 / 新国策树 / 新系统 / 新机制"（设计未定）
- 需求模糊，需要澄清（主题、版本、系统、资产、成功标准）
- 需要从 2-3 个方案中选一个

**何时不用**：
- 设计已批准 / 有 spec → 直接 **hoi4-writing-plans**
- 纯查询（语法/模板/报错含义）→ 知识层 skill，不启动流程链
- 单点小改动（改一个数值）→ 口头确认即可

## HARD-GATE（钢4版）

**设计未经用户批准，禁止创建或修改任何 mod 文件。**

但设计深度**按 mod 规模缩放**（防门过重，保快速迭代）：

| 规模 | 判定 | 设计产出 |
|---|---|---|
| **微型修改** | 单国策/单事件改数值、加一个决议 | **3-5 行 + 口头确认**，不写 spec |
| **小型扩展** | 新国家+国策树、新事件链 | **一页 spec**（关键字段：目标/涉及文件/本地化/验证） |
| **大型重构/新系统** | 新系统、多子系统联动、影响多个 mod | **完整 spec + 拆分建议**（分多个可独立验证的计划） |

## 探索上下文（先看再问）

- 读 mod 现状（目录结构、已有什么）
- git log（如果是 git 项目）看最近改动
- 读资料库导航 `references/README.md` 了解可用知识

## 澄清问题清单（一次一个，按序问）

| # | 问题 | 要点 |
|---|---|---|
| Q1 | **修改类型** | 小型扩展 / 大型重构 / 新国家 / 新系统 / 兼容补丁 |
| Q2 | **主题与设定** | 先世界观后内容（仿 TNO/KR：设定决定机制） |
| Q3 | **版本锚定** | 目标版本 1.17.x；MIO=1.14+/核心圈=1.16+/阵营重做=1.17+；跨版本调 **hoi4-version-migration** |
| Q4 | **涉及系统菜单** | 国策/事件/决议/人物/科技装备/MIO/阵营/核心圈/GUI/地图/音乐/成就/情报/子学说/意识形态（系统能力对照 **hoi4-advanced-systems**、**hoi4-gui-shader**、**hoi4-map-making**） |
| Q5 | **单人/团队** | 团队→Git 分支纪律 + 命名规范（仿 Rt56 强制 onboarding） |
| Q6 | **参考样本** | 原版国家 / 资料库 `13-完整示例工程\`（超事件/KR 欢迎页/曲线 Shader/电台）/ **hoi4-templates** 模板 |
| Q7 | **成功标准** | error.log 清零 + 至少一次 playtest（可测量） |
| Q8 | **资产来源** | 自绘 vs 复用原版 GFX |
| Q9 | **发布计划** | 是否发布创意工坊（→ 设计含发布要求） |

## 方案提案

- 给出 **2-3 个方案 + 明确推荐**（不只给一个）
- 比较维度：文件组织 / replace_path vs user_dir / 套改原版 vs 模板 vs 手写
- 推荐要说明理由（工作量、可维护性、兼容性）

## 分节呈现设计（逐节确认）

架构 → 数据流 → 资产 → 平衡基线 → 成功标准。每节让用户确认后再进下一节。

## 写 spec（非微型规模必写）

保存到 `docs/superpowers/specs/YYYY-MM-DD-<主题>-design.md`，**必含 7 项**：

1. **版本锚定声明**（1.17.x，含各系统版本门槛）
2. **系统清单**（涉及哪些系统菜单）
3. **文件清单草案**（按依赖链排序：本地化占位→GFX→想法→人物→国策→事件→决议→history）
4. **本地化方案**（语言、replace/ 需求）
5. **GFX 资产清单**（自绘 vs 复用，图标注册计划）
6. **平衡基线**（数值对照原版同类）
7. **成功标准**（可测量：error.log 清零 + playtest 内容）

## Spec 自查（5 项）

1. 版本语法一致性（无 1.14/1.16 旧语法混入）
2. ID 命名前缀规范（`my_mod_` 前缀，防冲突）
3. 资产需求不超能力（GFX/音乐是否可得）
4. 成功标准可测量（不是"尽量做好"）
5. 多子系统已拆分（各可独立验证）

## 出口

用户批准设计/spec → **唯一出口 = hoi4-writing-plans**。不批准 → 继续澄清或终止，不进入实现。

## 常见错误表

| 现象 | 原因 | 修复 |
|---|---|---|
| 设计没批准就写文件 | 跳过 HARD-GATE | 回到设计，先批准 |
| 小型 mod 被要求完整 spec | 门过重（没按规模缩放） | 微型=3-5 行口头确认；小型=一页 spec |
| 做出来的内容版本语法混用 | 版本锚定缺失 | Q3 必问，spec 含版本锚定声明 |
| 方案只给一个 | 没有比较空间 | 给 2-3 个方案+推荐 |
| 做完不知道"算不算成功" | 成功标准模糊 | Q7 必问：error.log 清零 + playtest |
| 设计用了 1.17 功能但没买 DLC | 忽略 DLC 依赖 | Q3/Q4 确认 DLC 可用性（阵营重做等需 DLC） |
